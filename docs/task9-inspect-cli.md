# Inspect capture CLI

The separate `src/inspect-cli.mjs` entry point connects the local capture wrapper
to the existing production CLI. The original `src/cli.mjs` command surface and
recovery command behavior are unchanged. This separation lets receipt readback run
without importing the production CLI or its transport dependencies.

## Commands

```text
node src/inspect-cli.mjs --help
node src/inspect-cli.mjs inspect <device-id> --run-directory <absolute-run-path>
node src/inspect-cli.mjs readback --run-directory <absolute-run-path>
```

Only the first and third commands are local-only. `inspect` is a real production
inspection when supplied a real device; implementation or a passing test suite
does not authorize invoking it. The historical uncertain inspection is still
unresolved. Do not run another physical inspect without separate authorization.

Choose and retain one reviewed absolute canonical run path before invocation,
under an existing owner-only 0700 parent. Use a neutral local label without device
IDs, addresses, tickets, or credentials. The run directory must not exist before
the first capture; it is created exclusively. Keep it after every outcome. Never
automatically create another path, delete an existing directory, or clear a lock
to bypass a blocked or uncertain operation. No root, device, or run is selected
automatically. The capture parent is not the runtime recovery store.

The parser permits exactly one `--run-directory`. `inspect` requires exactly one
syntactically valid device ID; `readback` permits none. Unknown/duplicate options,
relative/noncanonical paths, missing selectors, `latest`, `--apply`, and
`--prior-ticket` are rejected before capture or CLI loading.

## Execution and results

After the started marker is synchronized, `inspect` lazily imports the existing
CLI and awaits exactly:

```js
main(['runtime-recover', selectedDeviceId, '--inspect'], env, captureIo)
```

The environment is forwarded unchanged. Only the bounded capture stdout/stderr
sinks are passed as the runtime argument. There is no implicit preflight, detached
execution, additional timeout, retry, or subsequent command. Import/call failures
after capture entry retain uncertainty. The production transport's existing
timeouts, pinned host keys, exit checks, and stderr checks remain in effect.

The adapter prints one redacted JSON projection and returns the following exit
code. Finite results are emitted after receipt publication; publication failure
emits only uncertainty, and pre-invocation rejection emits only a blocked result.

| Outcome | Exit | Meaning |
| --- | --- | --- |
| FINITE_RESULT | 0 | Validated finite inspect result; stop and review |
| FINITE_STOP | 2 | Allowlisted inspect error; stop and review |
| BLOCKED | 3 | This invocation did not reach the production call |
| STOP_UNKNOWN | 4 | Result cannot be established; do not retry |

For a duplicate invocation, exit 3 says only that the duplicate did not run. It
does not change the earlier attempt's outcome. `actionable: true` and exit 0 do
not authorize apply. A readback with missing or invalid records exits 4.

If display fails, the on-disk receipt is retained and may be read back using the
same known path. An outer session loss must not trigger capture again. Readback
does not load the production CLI, choose a target, modify records, or repair a
partial publication. Its finite exit code describes the stored projection only.

The adapter now writes schema 2 receipts with a fixed `lastStage` label from the
controller or a validated Windows inspect rejection. This is the last stage reached, not an exact failure cause or proof
of Windows execution. Schema 1 receipts remain readable without an invented
stage. See [stage diagnostics](task9-inspect-stage-diagnostics.md) for labels,
crash behavior, local validation, and the remaining physical boundary.

## Validation and remaining boundary

Adapter tests inject a trusted stub loader for `main`; they verify exact argv,
environment/sink forwarding, awaited completion, one call, duplicate rejection,
finite exit mapping, input rejection, publication failure, and zero CLI loads
during readback. A real child process exercises the executable readback route
against a receipt generated by a stubbed inspection. No production inspect was
executed during this integration.

The [pre-CLI review](task9-pre-cli-readiness.md) remains the record of the capture
module's fault tests and limitations. Local self-review and tests are complete;
physical inspection, independent review, hardware power-loss guarantees, and
hostile-owner path-race protection are not established by this change.

Before physical use, review the exact device selection, retained local run path,
and invocation against the unresolved historical episode, then obtain separate
authorization for that one inspection. Reboot, apply, cleanup, doctor, baseline,
plan, and prepare are outside this adapter's command surface and authorization.
