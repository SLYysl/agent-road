# Remote exec latency: measured reduction

Date: 2026-09-19. Following the background coexistence check, the user authorized
latency diagnosis and optimization. All live probes were bounded background work;
no foreground input, reboot, package installation or Windows configuration change
was needed. The original revision was `6618eb2`.

## Measurement

The same fixed script printed `AGENT_ROAD_LATENCY_OK` with exit 0 and empty stderr.
Each iteration freshly loaded the production target and used the normal pinned
remote exec path. A process-runner observer recorded elapsed time without recording
host addresses, device IDs, keys, argument vectors or private paths. Ten original
runs preceded ten optimized runs. Pilot and exploratory probes are excluded.

| Metric | Original | Combined finalization |
| --- | --- | --- |
| Successful runs | 10/10 | 10/10 |
| Median, conventional midpoint | 9.810 s | 8.448 s |
| Mean | 9.934 s | 8.549 s |
| P95, nearest rank | 10.532 s | 9.224 s |
| Range | 9.566–10.532 s | 8.088–9.224 s |
| SSH calls per successful exec | 6 | 5 |
| SCP uploads per successful exec | 1 | 1 |

The observed median reduction is **13.9%**, or about 1.36 seconds. With only ten
samples, nearest-rank P95 is the maximum; it is not a well-estimated tail latency.
These are sequential runs under uncontrolled live workload, with local regression
tests also running during part of the optimized measurement. They do not establish
a general speedup or reliability rate. Total time includes target loading and local
cleanup, but excludes initial Node process/module startup. The user script does
almost no work, so its percentage improvement does not predict long-task speedup.

[Sanitized per-run timings](remote-exec-latency-2026-09-19.json) retain the measured
stage order and results. Initial target loading was roughly 12–33 ms across runs;
it was not the dominant cost. Separate successful probes measured a fresh SSH/cmd
round trip around 0.37 s and trivial PowerShell around 0.63–0.67 s. Production
wrapper calls were typically 1.3–2.0 s. Those measurements do not isolate network,
authentication and process startup perfectly.

## Change and compatibility

The successful path now reads and validates the canonical exit-code receipt and
cleans up the task's staging files in one fixed wrapper invocation. Its stdout
contains the exit code only after both phases pass. It reuses the original ACL,
path, reparse-point, size and canonical-record checks. Standalone read and cleanup
wrappers retain their original generated bodies for other callers.

Missing/malformed receipts remain `REMOTE_EXECUTION_UNCERTAIN`. A reported cleanup
failure remains `REMOTE_CLEANUP_UNCERTAIN`, even if a later bounded cleanup succeeds.
An unsuccessful or lost finalization response triggers the existing cleanup path,
never a replay of the user script. A confirmed successful finalization skips the
now-redundant standalone cleanup invocation. Main CLI result shape and user stdout,
stderr and exit-code semantics are unchanged. `finishedAt` is now sampled after
combined receipt/cleanup confirmation, slightly later in the successful lifecycle.

This is not persistent SSH, a shared shell or concurrent transport. Host-key
pinning, identity checks, serialization and uncertain-execution boundaries remain.
File-transfer workflows have not been changed by this optimization. Background
job control uses ordinary exec, so it shares this shorter bookkeeping path; its
end-to-end improvement was not independently benchmarked here.

## Validation and reproduction

The RED transport-count test observed six SSH calls where five were required.
Focused regression passed 137 tests with two platform skips. Full `npm test`
passed 1467 tests, skipped 17 and failed none (about 516 seconds). Physical Windows
checks additionally passed canonical receipt/exit 7, malformed receipt rejection
(exit 77), and rejecting a directory during cleanup (exit 78), without publishing
success early. An end-to-end script retained exit 7, exact Chinese/emoji stdout
and its expected stderr. Fixture artifacts were removed from their unique paths.

The explicit measurement tool keeps bounded, sanitized timings in OS temp and
stops at the first failed/uncertain operation without retry:

```sh
node src/cli.mjs measure-exec <device-id> 10
```

It accepts 1–20 iterations. Its summary uses nearest-rank P50/P95, while the table
above separately labels the conventional median. A physical one-run smoke check
of the committed tool's workflow also passed. No raw SSH arguments or credentials
are printed. The isolated Windows finalization fixture is generated by
`test/fixtures/exec-finalize.mjs`; run it only on an enrolled test device because it
uses unique entries in Agent Road's governed task staging directory.
